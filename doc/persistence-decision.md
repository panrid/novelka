# Рішення: розділити JDBC-сховище, відкласти ORM

Дата: 2026-09-20. Статус: JDBC-рішення збережено.

Доповнення після появи вебчиталки: server уже використовує Spring Boot для HTTP
та складання залежностей; CLI/core залишаються без Spring. Hibernate не додано.
ReaderDatabase застосовує міграції при старті і відкриває окреме з’єднання на запит.
Пулу поки немає. Деталі — [web.md](web.md). Нижче збережено обґрунтування початкового рішення.

## Контекст

Store поєднував SQL усіх сутностей, міграції, з'єднання та правила зміни словника.
SQL також був у CLI, Pipeline та OpenRouter. Це ускладнювало навігацію і перевірку
збереження витрат та відновлення перекладу.

Дані зараз переважно є JSONB-знімками глав, словника та Work. Окремі колонки потрібні
для пошуку, ревізій і журналу AI-викликів. Важливі явні контрольні точки, збереження
pending перед платним HTTP-запитом і session advisory lock на весь переклад новели.

## Рішення

Залишити JDBC та поточну схему; розділити SQL на п'ять тематичних репозиторіїв.
JdbcSession відповідає за з'єднання, транзакції та locks; MigrationRunner — за міграції.
DatabaseSession складає залежності на час команди. GlossaryService координує зміни,
які зачіпають словник, історію та стани залежних перекладів.

Публічні команди, JSON-поля, хешування, V1/V2 і наявні дані збережені.
Нових runtime-залежностей не додано.

## Чому не Spring Boot та Hibernate зараз

Spring Boot придатний і для CLI: він може запускатися без вебсервера.
Spring також підтримує як JDBC, так і JPA, тому Boot не вимагає Hibernate.
Hibernate підтримує JSON-мапінг; JSONB саме по собі не є перешкодою.

Але ORM зараз потребував би додаткових entity-мапінгів та перевірки життєвого циклу
знімків, а PostgreSQL-запити до історії, JSONB і advisory locks усе одно залишилися б.
У цій моделі поки мало об'єктних зв'язків, для яких ORM дає найбільшу користь.
Тому спершу розділено відповідальності без одночасної зміни способу зберігання.

Коли з'явиться сервер, повторно оцінюємо Spring Boot для конфігурації, DI, HTTP,
пулу з'єднань та транзакцій; JDBC/JdbcClient може залишитися для перекладів.
Hibernate/JPA варто окремо оцінити для реляційних сутностей користувачів і бібліотек.
Flyway доречний як наступна заміна ручного реєстру міграцій. Це плани, не поточні залежності.

## Умови майбутньої міграції

- Репозиторії однієї операції мають використовувати спільне з'єднання/транзакцію.
- Session advisory lock належить конкретному з'єднанню. Його не можна повернути
  в пул до звільнення lock; конкурентним командам потрібні окремі сесії.
- Не обгортати весь Pipeline у @Transactional: pending і контрольні точки мають
  фіксуватися до наступного HTTP-запиту, а не відкотитися разом із його помилкою.
- Вкладені JDBC-транзакції зараз приєднуються до зовнішньої без savepoint.
  Помилки потрібно передавати назовні для rollback.
- Зміни словника проходять через GlossaryService, щоб історія та інвалідація
  перекладів були атомарними.

Ціна поточного рішення: ручний SQL і складання залежностей, Map для деяких звітів,
міграції без checksum та відсутність пулу. Це прийнятно для CLI одного оператора;
саме розділення пакетів ще не робить застосунок готовим до паралельного вебнавантаження.

## Перевірка

Модульні тести перевіряють процес перекладу та OpenRouter через фікстури.
Інтеграційні тести використовують тимчасовий PostgreSQL: міграції V1 → V2,
аліаси, спільний rollback, ревізії, інвалідацію словника, звіти та відновлення
після збою. Платні API-виклики для цієї перевірки не потрібні.

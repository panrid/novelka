# Акаунти, редакторські правки та майстерня

[До змісту](README.md) · [Вебзапуск](web.md) · [Production](deployment.md)

## Ролі

| Роль | Доступ |
|---|---|
| Анонім | Каталог, зміст, публічні переклади |
| READER — читач | Реєстрація, вхід, власні пропозиції правок і їхній стан |
| EDITOR — редактор | Усе читача; черга всіх правок, погодження/відхилення чужих пропозицій |
| ADMIN — адміністратор | Усе редактора; імпорт, переклад, словник, витрати, експорт; призначення READER/EDITOR |
| OWNER — власник | Усе адміністратора; призначення ADMIN, реєстрація, налаштування ШІ та журнал дій |

Власник один. Публічна реєстрація завжди створює READER. Ніхто не може змінити
власну роль чи роль OWNER через API. ADMIN не змінює інших ADMIN і не призначає
ADMIN/OWNER. EDITOR не погоджує й не відхиляє власну правку: потрібен інший редактор.
Власник також дотримується цього правила розділення авторства і перевірки.

Приховані кнопки — лише зручність. AccessService перевіряє актуальну роль із БД
при кожній операції; пониження ролі діє для вже відкритої сесії. Воркера додатково
перевіряє автора завдання перед кожним етапом/AI-запитом.

## Створити власника

Перед першим запуском нової версії додайте у **локальний** `.env.local` або
**на VPS** `/opt/novelka/.env.production`:

```dotenv
NOVELKA_OWNER_USERNAME=panrid
NOVELKA_OWNER_PASSWORD='ваш-довгий-унікальний-пароль'
OPENROUTER_API_KEY='ваш-ключ'
```

Логін: 3–40 латинських літер/цифр, `_`, `-`, початок — літера/цифра;
нормалізується до нижнього регістру. Пароль: щонайменше 12 символів, не більше
72 байтів UTF-8. Значення вище — шаблони, не готові паролі.

У production env-файлі беріть пароль в **одинарні лапки**, особливо якщо він
містить `$`: без лапок або в подвійних лапках Compose підставляє змінні й може
змінити пароль. Апостроф усередині одинарних лапок у Compose env-файлі записується
як `\'`; правила цього файлу відрізняються від shell. Не виводьте весь
`docker compose config` у спільні логи — він містить розгорнуті секрети.
Правила: [Docker Compose env-синтаксис](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax).

Запустіть `./novelka-web` локально або виконайте звичайний deployment через GitHub
Actions. Власник створиться атомарно при старті, якщо його ще немає. Якщо логін
зайнятий звичайним користувачем, запуск відмовить: автоматичного підвищення немає.
Якщо OWNER уже існує, bootstrap не змінює його пароль або роль. Після створення
видаліть **обидва** NOVELKA_OWNER_* з env-файлу; при наступному відтворенні
контейнера вони перестануть передаватися. Власник лишиться у БД.

Увійдіть через «Увійти», відкрийте «Налаштування» й перевірте моделі та тарифи.
У «Користувачах» призначте потрібні ролі вже зареєстрованим акаунтам.
Ключ OpenRouter зберігається тільки в оточенні сервера, у браузер і журнал дій не потрапляє.

### Баланс OpenRouter у налаштуваннях

Власник може бачити поповнення, використання й залишок коштів у «Налаштуваннях».
OpenRouter надає баланс акаунта через `GET /api/v1/credits`, для якого потрібен
окремий [management key](https://openrouter.ai/docs/guides/overview/auth/management-api-keys).
Звичайний `OPENROUTER_API_KEY` використовується для перекладу й не відкриває
баланс акаунта. Додайте `OPENROUTER_MANAGEMENT_KEY` у `.env.local` або
`/opt/novelka/.env.production`, потім перезапустіть вебсервер. Ключ передається
тільки серверу, API віддає лише суми й доступне тільки OWNER. Якщо management key
немає, сторінка показує інструкцію замість суми. Кнопка «Оновити баланс» робить
новий запит; дані не кешуються у БД. Залишок обчислюється як поповнення мінус
використання, у доларах США.

## Вхід і захист запитів

Spring Security обробляє сесію, зміну її ID при вході, вихід і CSRF.
Паролі зберігаються як BCrypt із cost 12. Сесія має HttpOnly, SameSite=Lax,
8 годин бездіяльності; production Compose вмикає Secure, локальний HTTP — ні.
Сесії живуть у пам'яті сервера: після перезапуску потрібен повторний вхід.
Frontend не зберігає токен автентифікації в localStorage.

Перед кожним POST/DELETE клієнт отримує `/api/auth/csrf` і передає повернений
`token` у заголовку `headerName`. Це також потрібно для входу, виходу й реєстрації.
Вхід — form-urlencoded `username`/`password`; решта мутацій — JSON.
Усі API мають той самий origin; CORS для сторонніх сайтів не відкрито.
Вхід/реєстрація обмежені сумарно 20 спробами на IP за 10 хвилин на один сервер.
Ліміт у пам'яті, після рестарту скидається; це не розподілений антиспам.

## Правка від читача до публікації

1. Читач виділяє фрагмент одного абзацу й натискає олівець, який з'являється поруч.
   «Режим правок» над главою показує олівці для всіх блоків, включно із заголовком;
   він також дає змогу вибрати блок клавіатурою. Під час звичайного читання кнопки приховані.
2. Редагує весь абзац і за бажанням пояснює зміну. Виділення показується як орієнтир.
3. API зберігає `baseJobId`, індекс і ID блока, точний початковий текст, пропозицію,
   автора й дату. Публічні блоки не змінюються. Автор бачить власну версію з позначкою.
4. Редактор порівнює тексти в черзі та погоджує або відхиляє пропозицію.
5. Погодження атомарно створює нову `Work`-ревізію й записує рішення. Її видно
   всім читачам, у змісті й експорті. Старі ревізії та рішення не видаляються.

Погодження бере спільний lock новели з CLI/воркером. Зміна оригіналу, індексу,
ID або тексту відповідного блока спричиняє 409. Правки інших абзаців не заважають
погодженню: перевіряється актуальний текст, а не лише номер ревізії.
Власні pending-версії також відображаються тільки поки цей абзац й оригінал сумісні.
Повторне погодження заборонене. HTML у тексті відображається як текст.

`work_origins` пов'язує ручну ревізію з попередньою. Пошук контекстів словника
проходить цей ланцюжок: зміна використаного факту робить ручні ревізії
`needs-review` так само, як AI-переклад. Ручна правка не перераховує summary ШІ;
якщо вона змінює важливий факт сюжету, перевірте словник і за потреби запустіть вичитку.

## Майстерня перекладу

- **Переклад**: два основні кроки — імпорт Syosetu і переклад діапазону до 100 глав.
  Повторна вичитка та відновлення за job ID зібрані в «Додаткових операціях».
- **Дані новели**: українські назва, автор і опис, які бачать читачі; аліаси
  зібрані в окрему технічну секцію. Порожнє локалізоване поле прибирає його.
- **Словник**: коротка форма для японського написання, українського варіанта,
  типу, статі й контексту. Читання, альтернативні написання, впевненість,
  глава-джерело та стабільний ключ доступні в «Додаткових даних».
- **Глави й експорт**: історія ревізій, ручний імпорт оригіналу, HTML/EPUB.
- **Витрати**: групування за новелою/главою/етапом/моделлю або кожен запит,
  оцінена й підтверджена ціна, невідомі суми, токени та стан виклику.
  Натискання заголовка стовпця сортує всі завантажені рядки; повторне натискання
  змінює напрямок. Числа порівнюються як числа, невідомі значення завжди внизу.
  Для окремих запитів доступне сортування за часом. Перемикання між групами й
  окремими запитами скидає сортування.

Для імпорту 0–0 означає лише метадані. Звичайний переклад сам завантажує відсутні
оригінали. Повторний переклад готової глави потребує прапорця нової ревізії.
За потреби ручного джерела спочатку імпортуйте метадані новели, далі вставте текст.
Перший непорожній рядок ручного тексту стає заголовком, як у CLI.

Для нового запису стабільний ключ за замовчуванням дорівнює японському написанню;
для наявного він зберігається, тому зміна ключа створює інший запис. Збереження
використовує revision для захисту від втрати паралельних змін. Пропозицію ШІ можна
відкрити у формі, перевірити й зберегти вручну — вона не застосовується автоматично.

## Фонові завдання, бюджет і відновлення

Завдання і знімок налаштувань зберігаються у `web_tasks`. Один воркер тримає
глобальний session advisory lock 728620 весь час виконання; додатково береться
lock новели. CLI й веб використовують той самий Pipeline і PostgreSQL.
Мережеві AI-виклики виконуються поза довгими SQL-транзакціями.

Кожний платний запуск має **додатний додатковий бюджет на весь діапазон** й явне
підтвердження у формі. Веб не дозволяє безлімітний 0. Верхню межу одного запуску
задає OWNER, типово $5. Ліміт не є добовою квотою; декілька запусків складаються.
Резерв OpenRouter базується на тарифах зі знімка. Якщо реальний тариф змінився,
бюджет не гарантує точну фактичну суму: власник має підтримувати тарифи актуальними.

`web_task_jobs.initial_usd` фіксує вже враховані витрати перед відновленням;
`final_usd` — підсумок після завершення чи помилки. Подальше відновлення цього
job не збільшує історичну суму попереднього вебзапуску.
Облік запуску — приріст `actual_usd`, а де факт невідомий — `estimated_usd`.
Невідомі ціни не дорівнюють нулю. Повна історія лишається в `ai_calls`; ручні ревізії
не дублюють витрати їхніх предків. `job_metrics` зберігає токени й цільову оцінку.

Однаковий requestKey одного автора не створює два завдання. UI повторює ключ
при повторі того самого невдалого запиту; після успіху генерує новий.
Черга оновлюється кожні 5 секунд. Скасування зупиняє роботу між AI-запитами,
але не повертає гроші й не скасовує вже відправлений запит провайдеру.

Після аварії `running` стає `interrupted`, а не автоматично повторюється.
Перегляньте витрати й натисніть «Відновити» в картці завдання: ID підставиться автоматично.
`pending`/`uncertain` AI-виклик потребує окремого прапорця дозволу повтору:
перший запит уже міг коштувати грошей. Якщо оригінал змінився, потрібна нова ревізія.
Для `needs-review` потрібна вичитка або новий переклад, але попередній текст
лишається доступним читачам.

«Черга завдань» показує для кожного запуску операцію, новелу, діапазон глав,
поточну главу (коли вона відома), стан і витрати. «Подробиці» відкривають пояснення помилки, автора, час та ID
перекладу для відновлення. Для помилки зміни словника підказка веде до повторної
вичитки однієї глави через вебмайстерню.

### Помилки в черзі

Картка невдалого завдання показує пояснення та наступну дію, а не лише технічний
рядок. Старе `Dictionary tool limit exceeded` означає, що попередня версія зупинила
етап через шість пошуків. Тепер досягнення ліміту переводить модель до фінальної
відповіді з наявним контекстом. Для старого завдання натисніть «Відновити» і
задайте бюджет; змінювати словник тільки через цей ліміт не потрібно.
У «Додаткові опції словника» форми запуску задається 0–30 пакетних звернень на
етап сегмента (типово 6), до 20 слів одним зверненням. 0 вимикає лише додаткові
пошуки. Параметр зберігається в завданні, видно в подробицях черги та переноситься
у форму швидкого відновлення/повторного перекладу. Більше звернень може підвищити
витрати, але не скасовує бюджет. Для 401/403 показується перевірка ключа або доступу OpenRouter, для
429 — очікування до оновлення ліміту, а для `uncertain` — вимога спершу перевірити
витрати, бо запит уже міг бути оплачений.

### Перевірка пропозицій словника

Секція «Пропозиції ШІ» показує сторінки згрупованих унікальних пропозицій
із кількістю повторів та статусом: на перевірку, уже у словнику або відхилено.
Є пошук за вмістом пропозиції та порядок за часом або числом повторів. Нові коректні сутності аналіз може
додавати автоматично; наявні факти не перезаписуються без ручної дії.

«Відкрити у формі» підставляє наявний ключ сутності, якщо її знайдено, щоб
збереження альтернативного перекладу не створювало дубль лише через інший ключ.
Для можливого дубля можна відкрити канонічний запис прямо з пропозиції.
Збереження схожого нового запису поверне 409; наявні записи можна явно
об'єднати кнопкою біля форми. Під час активного перекладу запис/об'єднання
швидко повертає 409 з поясненням, а відхилення пропозиції залишається доступним.
«Відхилити» (ADMIN/OWNER) приховує однакові пропозиції цієї новели, включно з
майбутніми повторами. Відмінна за змістом версія знову потрапляє на перевірку.
Відхилення не видаляє й не змінює канонічний запис, не позначає глави на вичитку;
воно фіксується в аудиті. Загальна кількість історичних записів залишається окремою.

## Сповіщення і швидкі дії

Дзвіночок у шапці доступний після входу. Непрочитані події мають лічильник;
натискання відкриває главу, словник або конкретне завдання, навіть якщо воно вже
поза першою сторінкою черги. Подію можна позначити прочитаною окремо або кнопкою
«Прочитати всі». Стан зберігається в PostgreSQL окремо для кожного акаунта.

| Подія | Хто бачить | Коли з'являється |
|---|---|---|
| Нова глава | READER і вище | Перша завершена публікація глави з актуальним оригіналом |
| Нові записи словника | ADMIN, OWNER | Нові ключі в канонічному словнику, кількість за одну ревізію |
| Завдання завершено | ADMIN, OWNER | Успішне завершення всього запуску |
| Помилка / переривання | ADMIN, OWNER | Збій завдання або відновлення сервера після переривання |

Заголовок події завдання будується зі збереженого запиту `web_tasks`, а не з журналу:
операція (`task_operation`) і глави (`task_first`/`task_last`, для відновлення —
`task_job_chapter` з job). Наприклад: «Переклад завершено: глави 7–10»,
«Вичитку завершено: глава 15», «Імпорт завершено: лише опис новели». Назва новели
показується окремим рядком. Якщо завдання не знайдено, лишається загальний текст.

Поки немає персональних підписок, сповіщення про глави стосуються всіх новел.
Акаунт бачить події від моменту своєї реєстрації. Історичні переклади під час
оновлення не створюють масових сповіщень. Зміна вже відомого слова чи пропозиція,
яка ще не потрапила до словника, не вважається новим записом.

Список оновлюється кожні 15 секунд, коли вкладка видима, і після повернення до неї.
Нова подія показує невелике повідомлення на сайті; після закриття вкладки події
залишаються в історії дзвіночка. Email та системні push-сповіщення не надсилаються.

У невдалому або перерваному завданні є швидкі дії:

- «Відкрити словник» — для помилок словника, з переходом одразу до потрібної новели.
- «Відновити» — якщо job є останньою незавершеною ревізією з актуальним оригіналом.
- «Повторно вичитати» — після зміни словника, якщо остання ревізія має всі чернетки.
- «Перекласти главу заново» — підставляє поточну главу як одиночний діапазон і вмикає нову ревізію.

Ці кнопки лише готують форму. Потрібно вказати додатковий бюджет і підтвердити
платні запити. Дозвіл повторювати `uncertain` ніколи не вмикається автоматично.
Якщо поточна глава невідома, інтерфейс не вгадує її для багатоглавного запуску.
Перед фактичним запуском воркер повторно перевіряє актуальність job.

## Налаштування вебу та CLI

Веб бере моделі/тарифи/розмір сегмента з `site_settings`, а CLI — зі своїх env-змінних.
Зміна вебналаштувань **не змінює** CLI й уже поставлені в чергу завдання.
Початкові вебзначення: gpt-4o-mini на трьох етапах, $0.15/$0.60 за млн токенів,
1500 символів сегмента, ціль $0.10/5000 токенів. Це конфігураційні значення,
не автоматичне отримання актуального тарифу OpenRouter.

JSON-контракти запитів описані окремими Java record. Примітивні поля TaskRequest
потрібно передавати явно, включно з false для force/retryUncertain.

## Перевірки й межі

AccessIntegrationTest використовує реальний HTTP і тимчасовий PostgreSQL:
CSRF, сесії, ролі, приватні правки, конфлікти, ручні ревізії, словник, чергу,
ідемпотентність, скасування, бюджет діапазону та налаштування.
AI у тесті воркера — підміна, платних запитів немає. Playwright перевіряє
desktop/mobile сценарії через тестові API; production JAR збирається окремо.

Ще не реалізовані email-підтвердження/скидання пароля, персональні бібліотеки
із синхронізацією між пристроями, оплати й ілюстрації. Зміна пароля через UI
також потребує окремого наступного етапу; bootstrap не є механізмом його скидання.

# Таблиці й великі списки

## Карта списків

| Список | Екран | API | Доступні параметри |
|---|---|---|---|
| Каталог | CatalogPage, вибір у ManagePage | `GET /api/novels/search` або `/api/novels` | `q`, `readyOnly`, `sort=title\|author\|ready\|id` |
| Зміст новели | NovelPage | `GET /api/novels/{id}/contents` | `q` за назвою/номером, `sort=number` |
| Користувачі | AccountsPage | `GET /api/accounts` | `q`, `role`, `sort=created\|username\|role` |
| Журнал дій | AuditPage | `GET /api/accounts/audit` | `q` за виконавцем/об'єктом, `action`, `sort=created\|actor\|action` |
| Правки | CorrectionsPage | `GET /api/corrections` | `queue`, `q` за текстом, `state`, `novel`, `sort=created\|state\|chapter\|novel` |
| Черга | TaskQueue | `GET /api/tasks` | `q` за новелою/ID, `state`, `operation`, `novel`, `sort=created\|state\|novel\|spent` |
| Витрати | CostReport | `GET /api/manage/costs` | `novel`, `details`, `q`, `stage`; сортування за видимими числовими, текстовими й часовими колонками |
| Ревізії | JobTable | `GET /api/manage/{id}/jobs` | `q` за номером/ID, `state`, `sort=updated\|chapter\|revision\|state` |
| Словник | GlossaryEditor | `GET /api/manage/{id}/glossary/entries` | `q`, `kind`, `sort=japanese\|ukrainian\|kind\|chapter` |
| Пропозиції ШІ | GlossaryEditor | `GET /api/manage/{id}/proposals` | `q`, `sort=created\|occurrences` |
| Сповіщення | NotificationBell | `GET /api/notifications` | `before` — курсор ID для старіших подій |

Для перших десяти endpoint спільні `page` (від 1), `size` (1–100, типово 25),
`q` (до 200 символів), `sort` і `direction=asc|desc`. Відповідь:
`{items,page,size,total,totalPages}`. Невідоме поле сортування, фільтр або
розмір дає 400. Назви колонок беруться з whitelist у репозиторії, а значення
передаються в параметризовані SQL-запити. SQL виконує фільтрацію, порядок і
`LIMIT/OFFSET`; frontend не сортує лише поточну сторінку як увесь набір.
До кожного порядку додано стабільний додатковий ключ, щоб сусідні сторінки не
переставляли записи з однаковим основним значенням. При одночасному записі
offset-сторінки можуть зсунутися; для потоку сповіщень використано курсор `id`.
Відповідь сповіщень містить `items` (до 30), `unread`, `latestId` і
`nextCursor` (0 означає кінець). Нові події не пересувають стару сторінку.

`frontend/src/components/ListTools.tsx` містить невеликі складники: `useListState`,
`listParams`, `ListSearch`, `ListFilter`, `ListPages`, `ListEmpty` і `TableHeader`.
Стан сторінки, запиту, фільтрів та порядку зберігається в hash URL. Для кількох
списків майстерні використовуються префікси `task_`, `cost_`, `job_`, `gloss_`,
`proposal_`. Пошук відкладає запит на 300 мс; зміна пошуку, фільтра чи порядку
повертає на сторінку 1. Якщо остання сторінка стала порожньою після редагування,
`ListPages` переходить на останню наявну. `useResource(..., true)` зберігає
попередні рядки до відповіді й показує «Оновлюємо…»; помилка API показується
окремо з повтором. Порожній набір і порожній результат пошуку мають різні тексти.

`TableHeader` дає клікабельний на всю назву заголовок, стрілку напрямку й
`aria-sort`. Пояснення колонки відкривається через `<details>`: миша, клавіатура
й дотик працюють без hover. Для вузьких екранів таблиці прокручуються по горизонталі
з мінімальною шириною, щоб слова не ламалися на кілька літер. Деталі довгого
аудит-запису розгортаються лише за потреби.

Сторінка `GET /api/manage/{id}` повертає метадані, кількість імпортованих глав і
ревізію словника. Записи, пропозиції й історія jobs читаються окремо. Схожі
імена для редактора: `GET /api/manage/{id}/glossary/similar?japanese=...&ukrainian=...&kind=...`;
це підказка, а не автоматичне об'єднання. Новий запис із можливою копією
сервер відхиляє 409; явне `POST /glossary/merge` з revision, keepKey, removeKey
зберігає основний запис, додає написання/факти іншого й позначає залежні
переклади на перевірку. Якщо pipeline тримає lock новели, збереження/об'єднання
повертає 409 одразу. Відхилення пропозиції не залежить від цього lock.

Схема V6 додає індекси для порядку за часом та фільтра власних правок,
завдань, ревізій, аудиту й пропозицій. Пошук `ILIKE '%...%'` не отримав
випадкового btree-індексу: він не прискорить такий запит. Якщо обсяг даних
потребуватиме триграмного індексу, потрібні виміри на production-подібній БД
й окреме рішення про `pg_trgm`. Пропозиції групуються у SQL за нормалізованим
JSON (без технічного ключа/глави, з упорядкованими alias), а статус і зміст
пропозиції порівнюються з канонічним словником у сервісі.

Короткі або контекстні набори залишаються без сторінок: аліаси однієї новели,
варіанти ролей/операцій, одна глава в читалці, локальні особисті правки глави.
У читалці сервер повертає лише номер попередньої й наступної доступної глави,
тому навігація не завантажує весь зміст.

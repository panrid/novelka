# Розробка і перевірки

[До змісту](README.md) · [Карта коду](architecture.md) · [Рев'ю](refactoring-review.md)

## Стиль

`.editorconfig` є спільним налаштуванням для IDE:
UTF-8, LF, 4 пробіли на рівень вкладення, tab width 4.
Для IntelliJ Java continuation indent — 8; YAML лишається з 2 пробілами.
Кнопка Tab має вставляти пробіли, literal tab у Java не використовується.
Кожен клас, record та interface — в окремому файлі; вкладені типи не додаємо.

Автоматичної Gradle-задачі форматування/перевірки стилю наразі немає.
EditorConfig керує редактором, але не є CI-перевіркою.
Застосовані міграції можна переформатувати без зміни SQL; нова семантика потребує нової версії.

## Команди перевірки

```sh
./gradlew test
./gradlew :core:integrationTest :server:integrationTest
./gradlew :core:liveSourceTest
./gradlew :cli:installDist
sh -n novelka
git diff --check
```

| Набір | Що перевіряє | Інфраструктура |
|---|---|---|
| core:test | Парсер, словник, сегменти, pipeline, mock OpenRouter, HTML/EPUB | Локальний HTTP для частини тестів |
| cli:test | Launcher: інша директорія, пробіли у шляхах, env, помилка збірки | Тимчасові shell-фікстури, без БД і реального Gradle |
| core:integrationTest | SQL, ревізії, словник, аліаси, відновлення з mock HTTP | Embedded PostgreSQL в тимчасовому каталозі |
| server:integrationTest | HTTP API, аліаси, готові ревізії, зміни оригіналу та відмови | Embedded PostgreSQL та локальний HTTP |
| frontend: npm test | Каталог, читалка, правки, сортування витрат, селектори, mobile | Playwright Chromium і WebKit, API-фікстури; спочатку npm run build |
| core:liveSourceTest | Реальний API і HTML Syosetu | Інтернет |

Тести не звертаються до платного OpenRouter. integrationTest та liveSourceTest
не входять у звичайний test; зеленого test недостатньо для підтвердження SQL-змін.
Звіти: `<module>/build/reports/tests/<task>/index.html`;
машиночитні результати — `<module>/build/test-results/<task>`.

## Якщо PostgreSQL у тесті не стартує

Інтеграційні фікстури передають stdout/stderr дочірніх процесів у консоль.
Читай конкретну помилку initdb/postgres, а не лише initializationError.
Зафіксований приклад — `shmget ... Operation not permitted` у процесі Gradle,
який успадкував sandbox-обмеження; прямий initdb поза ним міг працювати.

Спробуй `./gradlew --no-daemon :core:integrationTest` у звичайному терміналі,
щоб використати свіжий процес. Це не універсальне виправлення: якщо ОС забороняє
shared memory чи мережеві сокети, потрібен запуск у відповідному середовищі.
Не позначай тест пропущеним лише для зеленого результату.
Ручний smoke-тест кількох CLI-команд на Docker не замінює весь integrationTest.

## Додати команду

1. Створи окремий клас у cli.command або тематичному підпакеті.
2. Успадкуй DatabaseCommand, якщо потрібна БД, або AiCommand для моделі й бюджету.
3. Додай клас до subcommands у Novelka або груповій команді.
4. Розпізнай NOVEL через novelId до lock; не зберігай аліас у jobs/chapters.
5. Валідуй аргументи до запису даних; транзакцію використовуй для зв'язаних змін.
6. Онови cli.md і додай перевірку поведінки, де можлива регресія.

Не додавай HTTP-виклики до SQL-транзакцій: вони можуть тримати locks хвилинами.
Session lock новели під час pipeline — окреме свідоме рішення, яке запобігає
конкурентній зміні словника/перекладу тієї самої новели.

## Додати операцію з даними

SQL додавай у відповідний клас core.repository; технічні операції зі з'єднанням —
у core.persistence. CLI та інтеграції не повинні викликати JdbcSession напряму.
Правила, що зачіпають кілька репозиторіїв, належать тематичному сервісу.

У межах команди використовуй репозиторії одного DatabaseSession, щоб усі записи
брали участь у спільній транзакції. Зміни канонічного словника проводь через
GlossaryService.update: прямий GlossaryRepository.save не виконає інвалідацію перекладів.
Репозиторій не повинен самостійно відкривати нове з'єднання.

## Змінити міграції

Додай `core/src/main/resources/db/V<N>.sql`, збільш верхню зареєстровану версію
в MigrationRunner.LATEST_VERSION і перевір як чисту базу, так і оновлення попередньої схеми.
Зараз немає Flyway, автосканування ресурсів чи перевірки checksum міграцій.
Файл SQL сам по собі не запускається, якщо версію не зареєструвати.

## Змінити промпт/модель

Промпти — окремі ресурси analyze.txt, translate.txt, proofread.txt.
Їхній хеш впливає на prompt_version, а текст — на збережений request context.
Не змінюй JSON-контракт без узгодження OpenRouter.responseFormat/normalize і Pipeline.
Реальний літературний тест потребує окремого свідомого запуску з бюджетом.
Модульні тести підтверджують структуру й відновлення, не точність перекладу.

## Межі, які ще потребують роботи

- Pipeline ще приймає DatabaseSession як набір залежностей; перед сервером варто
  звузити його залежності до потрібних репозиторіїв та контракту транзакцій.
- OpenRouter поєднує HTTP, промпти, бюджет і повторне використання відповідей.
  SQL вже винесений у AiCallRepository; решту відповідальностей можна розділяти окремо.
- ApplicationContext статичний; CLI-тестування прикладної логіки через ін'єкцію залежностей
  ще не організоване. Launcher-тести цього не покривають.
- Стани Work/Segment/AiCall задані рядками, а не enum; зміна потребує сумісності з JSON/SQL.
- Resume працює зі збереженим Work і не перевіряє новий sourceHash так, як create.
  Proofread теж зберігає старий sourceHash; за зміненого оригіналу використовуй translate --force.
- ID блоків можуть повторюватися між главами в HTML-експорті; варто зробити глобальні якорі.
  React-читалка рендерить одну главу й не використовує ID блоків як HTML id.
- Немає редактора пропозицій, dry-run оцінки всього діапазону чи інтерактивного меню.
- Поточний ключ новели — ID Syosetu; перед другим джерелом потрібна схема ідентичності
  з урахуванням джерела, щоб однакові зовнішні ID не конфліктували.

Це напрями наступних окремих змін. Поточне рев'ю не означає, що весь core вже
готовий до багатокористувацького вебзастосунку.

# Вебкаталог і читалка

[До змісту](README.md) · [Архітектура](architecture.md) · [CLI](cli.md)

## Що вже працює

- Каталог із пошуком за назвою, автором, ID та аліасами.
- Фільтр новел із готовими главами.
- Сторінка новели зі змістом і кількістю доступних глав.
- Каталог і зміст завантажуються порціями з серверним пошуком; стан списків є в URL.
- Читалка: заголовки, абзаци, передмова, післямова, розділювачі сцен.
- Переходи між доступними главами, навіть якщо номери йдуть із пропусками.
- Розмір тексту 16–28 px і спільна для всього сайту тема: світла, темна, чорна або системна
  з фоном #000000. Темна тема увімкнена за замовчуванням. Перемикач «Тема» —
  сегменти «Світла | Системна | Темна | Чорна» (радіогрупа, стрілки змінюють вибір);
  у шапці й на вузьких екранах лишаються значки з доступними підписами. Він у шапці
  й читалці зберігає вибір у `localStorage` (`novelka:theme`); обидва синхронізовані
  через ThemeContext. Системна тема відстежує `prefers-color-scheme`; типовою
  залишається темна. Палітра задається CSS-змінними, колір панелі браузера — theme-color.
- Продовження з останньої відкритої глави в цьому браузері.
- Мобільна верстка, клавіатурна навігація, завантаження, порожні стани та повтор після помилки.
- Правки без постійних написів між абзацами: олівець після виділення фрагмента
  або кнопки для всіх абзаців у «Режимі правок» над главою.

Селектори майстерні, словника та ролей використовують спільний `SelectField`:
список має тему сайту, прокрутку та позначення вибраного пункту. Підтримуються
стрілки, Home/End, пошук початком назви, Enter/пробіл, Escape, Tab і закриття
кліком поза списком. Список рендериться через portal, щоб таблиці та панелі не
обрізали його; позиція враховує краї екрана. Це заміна системного меню select,
вигляд якого браузери, зокрема Safari, контролюють самі.

Каталог і сторінка новели показують українські `titleUk`, `authorUk` і `descriptionUk`,
якщо вони задані. Для назви й автора порожнє локалізоване поле повертає значення
джерела; опис за відсутності не показується. Ці поля редагує ADMIN у «Дані новели».
Заголовки глав беруться з перекладу.
Обкладинки — декоративне оформлення CSS, не зображення із Syosetu і не згенеровані ілюстрації.

Доступні акаунти, ролі, редакторські правки й адміністративна майстерня:
імпорт, переклад, вичитка, словник, витрати та експорт. Дивіться
[Акаунти й майстерня](accounts-and-management.md), включно зі створенням власника.
Налаштування (`#/settings?section=…`) розбиті на категорії: «Загальні» (реєстрація),
«ШІ та моделі» (баланс OpenRouter, моделі й тарифи етапів), «Переклад» (бюджет,
цільова ціна, розмір сегмента), «Редагування та погодження» (власні правки
адміністратора) і «Вигляд» (тема). ADMIN бачить лише «Користувачі та ролі» й «Вигляд», OWNER — усе.
Користувачі живуть тільки тут: список із пошуком за ніком або email, а вибраний
користувач відкривається в широкій панелі з картками ролей і поясненням, що кожна
дозволяє, та історією ніків. Стара адреса `#/accounts` переспрямовує сюди. Порожніх категорій немає: нова категорія
з'являється разом із першим її налаштуванням. Незбережені зміни зберігаються при
переході між категоріями й записуються однією кнопкою. Баланс OpenRouter видно, якщо
сервер має окремий management key.

Каталог моделей (`server/models`) не прив'язаний до провайдера: `ModelDirectory` уміє
отримати список, `OpenRouterModelDirectory` читає публічний `GET /api/v1/models`
(`novelka.openrouter.models-url`). Ціни OpenRouter — долари за токен; сервер переводить
їх у долари за мільйон. Придатна модель має текстові вхід і вихід, `response_format`
або `structured_outputs`, `tools` і фіксовану ціну; решта показується з причиною.
Список зберігається в `model_catalogs` з часом оновлення й оновлюється не частіше
ніж раз на 12 годин або кнопкою власника. Якщо API недоступне, лишається останній
успішний список, а в полі можна ввести будь-яку назву моделі вручну.

Кожен етап має прапорець `catalogPricing`. Нове завдання тоді бере ціну з
збереженого каталогу (без мережевого запиту), але лише якщо відомі обидві ціни;
інакше діють ручні тарифи. Каталог ніколи не перезаписує збережені ручні ціни.
Налаштування, збережені до цієї версії, мають `catalogPricing=false`.

Форма запуску в майстерні має згорнутий блок «Розширені параметри»: модель для
цього завдання, повторний переклад готових глав і ліміт звернень до словника.
Перевизначення передається як `overrides: { model }` (`ExecutionOverrides` — місце для
майбутніх параметрів виконання). Воно діє на всі ШІ-етапи лише цього завдання,
не змінює налаштувань сайту й потребує придатної моделі з відомими цінами в каталозі,
щоб бюджет лишався контрольованим; для імпорту перевизначення заборонене. Знімок
`web_tasks.settings` зберігає фактичну модель і ціни, а подробиці завдання показують,
чи модель була за замовчуванням, чи перевизначена. Черга майстерні показує короткий стан і витрати кожного завдання;
помилки, час та ID перекладу відкриваються в подробицях.
Синхронізації читацького прогресу між пристроями ще немає.
Зберігається номер відкритої глави, а не позиція прокрутки або факт прочитання.

## Запуск однією командою

Передумови: JDK 25, Node.js 22.12+ з npm, PostgreSQL із параметрами у .env.local.

```sh
# Якщо PostgreSQL ще не запущено:
docker compose --env-file .env.local -f infra/compose.yaml up -d --wait

# З кореня репозиторію:
./novelka-web
```

Відкрити [http://127.0.0.1:8080](http://127.0.0.1:8080), зупинити Ctrl+C.
OPENROUTER_API_KEY для роботи читалки не потрібен.

Launcher читає .env.local за тими самими правилами, що й novelka.
NOVELKA_ENV_FILE задає інший файл; відносний шлях рахується від поточного каталогу.
Невдале збирання зупиняє запуск, тому старий JAR випадково не стартує.

```sh
NOVELKA_ENV_FILE=.env.translation.local ./novelka-web
./novelka-web --server.port=8081
```

Gradle-задача :server:bootJar встановлює npm-залежності через npm ci, перевіряє
TypeScript, збирає Vite та включає frontend/dist у BOOT-INF/classes/static.
Результат — server/build/libs/novelka-server.jar. Повторні незмінені задачі пропускаються.
:cli:installDist не запускає npm і не пакує сайт.

## Розробка з автоматичним оновленням UI

У першому терміналі з кореня завантаж конфігурацію БД і запусти API:

```sh
set -a
. ./.env.local
set +a
./gradlew :server:bootRun
```

У другому:

```sh
cd frontend
npm ci
npm run dev
```

Відкрити [http://127.0.0.1:5173](http://127.0.0.1:5173).
Vite пересилає /api на 127.0.0.1:8080; у цьому режимі порт API має лишатися 8080,
або потрібно змінити proxy у vite.config.ts.
bootRun запускає API; зібраний frontend додається саме у bootJar.
npm run preview показує production-збірку на 4173 із таким самим proxy.

## Конфігурація і межі

| Параметр | Значення за замовчуванням |
|---|---|
| NOVELKA_DB_URL | jdbc:postgresql://localhost:5432/novelka |
| NOVELKA_DB_USER | novelka |
| NOVELKA_DB_PASSWORD | novelka |
| NOVELKA_SERVER_PORT | 8080 |
| server.address | 127.0.0.1 |

Локально сервер слухає loopback. Spring Security забезпечує сесію й CSRF;
сервер перевіряє актуальні ролі для операцій запису. Production використовує
HTTPS через контейнер Caddy; конфігурація — у [deployment.md](deployment.md).
Frontend не читає кореневі env-файли й не містить API-ключів.
Spring не повертає stack trace або повідомлення внутрішніх винятків через API.

Публічні GET `/` і `/index.html` мають бути дозволені обидва: Spring Boot
пересилає запит welcome page з `/` на `/index.html`, а Spring Security
перевіряє цей внутрішній forward повторно. Дозвіл тільки `/` спричиняє 401
замість головної сторінки навіть при успішному запуску сервера.
ReaderIntegrationTest перевіряє цей сценарій із тестовою статичною сторінкою,
доступ до assets та збереження захисту адміністративних API.

## API

| Метод і шлях | Результат |
|---|---|
| GET /api/novels | Сторінка NovelCard: id, title, author, description, chapterCount, readyChapters, aliases |
| GET /api/novels/search | Сторінка NovelCard із `q`, `readyOnly`, `sort`, `direction`, `page`, `size` |
| GET /api/novels/{idOrAlias} | NovelDetail: назва, автор, опис, chapterCount, readyChapters, firstChapter; необов’язковий `resume` перевіряє, чи збережена глава ще опублікована, і повертає `resumeChapter` |
| GET /api/novels/{idOrAlias}/contents | Сторінка ChapterSummary з пошуком за назвою/номером |
| GET /api/novels/{idOrAlias}/chapters/{number} | ReaderChapter: текст, особисті правки й номери сусідніх доступних глав |

ChapterSummary містить number, title, revision. Block містить id, kind, text.
Невідома новела/недоступна глава — 404; нечисловий або непозитивний номер — 400.
`personalReplacements` містить лише сумісні непогоджені правки поточного читача
за індексом блока. Для аноніма це порожній об'єкт. Public `blocks` не підміняються.
Контракти операцій запису й правила ролей описані в [майстерні](accounts-and-management.md).

Глава доступна, якщо її остання придатна до публікації ревізія має state=complete
або needs-review і sourceHash відповідає поточному оригіналу. Поки нова ревізія
незавершена, читалка показує останню готову; needs-review лишається доступним,
щоб зміна словника не знімала текст із сайту.
Читалка отримує лише revised-блоки, без чернеток, оригіналу й контексту AI.

ReaderRepository формує проєкції: каталог і зміст не передають повні тексти глав.
Читалка отримує попередній/наступний номер із сервера, тому не завантажує
весь зміст для двох навігаційних посилань. `/api/novels` і
`/api/novels/search` повертають той самий сторінковий контракт.
ReaderService відкриває новий JdbcSession на HTTP-запит і закриває його через
try-with-resources. Міграції виконуються один раз у ReaderDatabase при запуску.
Схема PostgreSQL — V9; окремої копії бази для фронтенду немає.
`GlossaryEditor` окремо отримує сторінки записів і згрупованих пропозицій зі
статусом, кількістю повторів та наявним `canonicalKey`; відхилення й об'єднання
надсилаються на сервер із CSRF. Контракт списків описано в [lists.md](lists.md).
`TaskForm` передає `dictionarySearchLimit`, зміна ліміту скидає підтвердження бюджету.
`frontend/notifications/NotificationBell` опитує API сповіщень кожні 15 секунд,
зберігаючи прочитання на сервері. Параметри `#/manage?novel=ID&task=ID` відкривають
конкретне завдання; `tab=glossary` відкриває словник. `TaskPreset` передає
підготовлену швидкою дією операцію у `TaskForm`, без бюджету й дозволу uncertain.
Права та поведінка подій описані в [акаунтах і майстерні](accounts-and-management.md).
Адміністративний DatabaseSession також ідемпотентно перевіряє міграції при відкритті.

## Навігація у коді

| Каталог | Відповідальність |
|---|---|
| frontend/src/pages | CatalogPage, NovelPage, ReaderPage |
| frontend/src/auth, management | Сесія, форми й черга адміністративних операцій |
| frontend/src/components | Спільні loading/error стани |
| frontend/src/api | TypeScript-контракти та HTTP-клієнт |
| frontend/src/hooks | useResource: завантаження, скасування застарілих запитів, retry |
| frontend/src/lib | URL-маршрути та localStorage з обробкою відмови сховища |
| frontend/src/App.tsx | Оболонка, hash-маршрути, header/footer |
| frontend/src/styles.css | Адаптивна верстка і тема |
| server/controller, service, dto, config | HTTP, прикладне читання, response-моделі, JDBC |
| server/account, security, correction, settings, task, repository | Акаунти, захист, правки, конфігурація, фонова робота, SQL |
| core/repository/ReaderRepository.java | SQL доступних для читання ревізій |

Адреси виглядають як /#/novels/n0022gd/chapters/1: оновлення вкладеної сторінки
не потребує серверних правил перенаправлення. API завжди викликається з того самого origin.
Ключі localStorage мають префікс novelka:; прогрес використовує канонічний ID.

## Перевірки

```sh
./gradlew test :core:integrationTest :server:integrationTest
./gradlew :server:bootJar
sh -n novelka novelka-web

cd frontend
npm ci
npm run build
npx playwright install chromium webkit
npm test
```

ReaderIntegrationTest піднімає тимчасову PostgreSQL і справжній Spring HTTP-сервер:
перевіряє аліаси, каталог, блоки, доступність попередньої готової ревізії та
приховування перекладу після зміни оригіналу.
та помилки API. WebLauncherTest перевіряє шляхи з пробілами, env-файли та збій збірки.
AccessIntegrationTest перевіряє справжні сесії/CSRF, ролі, ревізії правок,
словник, ідемпотентність, бюджет діапазону та фонову чергу з підміною ШІ.

Playwright виконує сценарії для desktop і mobile Chromium та desktop WebKit (рушій Safari). API у браузерних тестах
підмінений фікстурами; реальний API перевіряється окремо інтеграційними тестами.
Перевіряються пошук, фільтр, навігація, прямі посилання, теми, localStorage,
помилки та відображення HTML-подібного тексту без його виконання.
Додані сценарії входу, відправлення/погодження правок, рольової навігації й
запуску платного завдання з обов'язковим бюджетом і підтвердженням.
Перевіряються також сортування витрат з невідомими сумами, клавіатурний вибір
у селекторах, закриття списку та пропонування правки після виділення тексту.
Ці перевірки не оцінюють літературну якість перекладів.

Каталог, зміст, акаунти, правки, аудит, черга й історії майстерні мають
сторінкові запити. Наразі воркер виконує одне
завдання за раз. Оплати, бібліотеки між пристроями й email-відновлення ще попереду.
